# Z119 application startup and the remaining linkage boundary

The initial function inventory did not recover all address-taken application
code. `discover_function_entries.py` identifies 5,810 aligned Xtensa `ENTRY`
candidates. Of 542 omitted from the initial inventory, 441 have aligned
original pointer occurrences. The discovery pass defines 436, leaves two
overlaps untouched, and rejects three. The other 101 unreferenced candidates
still require review. This produces 5,710 functions / 5,709 decompilations;
the one existing failure at `0x40083794` remains. This is not an exhaustive
function inventory or a claim that all inferred boundaries are correct.

`startup-bindings.json` records the exact input identity, the verified bytes
behind key literal bindings, instruction-export hashes, and the real static
initialization array. It is generated by `tools/recover_startup.py`. All
recorded instruction bytes are checked against the mapped original image.

## Boot and Core construction

The static initialization runner at `0x40134560` calls the **45 pointers** at
`0x3f48581c` through `0x3f4858cc` in descending address order. This is established
by the actual runner's pointer loop, not merely by pointer-shaped data.

Original `app_main` at `0x400ee978` calls `initArduino` and creates
`coreLoopTask`, entry `0x401218d4`, with 16,384 stack bytes, priority 1 and CPU
affinity 1. The task invokes bootstrap `0x4012186c`, which initializes Serial
at 115200 with configuration `0x0800001c`, allocates `0x15ab8` bytes, calls
the Core constructor `0x40120a04`, stores the result at global `0x3ffc2e88`,
and calls its virtual setup. The loop repeatedly yields, reads milliseconds,
and invokes the Core tick. Core's vtable at `0x3f41feb4` binds setup at
offset 12 to `0x40113078` and tick at offset 16 to `0x40120120`.

Recovered subobjects include CoreState at `+0x730`, RuntimeState at `+0xa20`,
HeaterState at `+0x9d8`, thermal flags at `+0xc50`, SensorsState at `+0xc58`,
MAX11613 at `+0x48b4`, Heater at `+0x4940`, and Runtime at `+0x12bd0`.
These offsets identify original objects; the owned portable types deliberately
do not pretend to reproduce an ESP32 C++ vtable layout in a host process.

## Actual platform bindings

`platform/esp32/esp32_platform.cpp` calls the real historical SDK interfaces.
It supplies GPIO, I²C, MSP transport, SPI, partition lookup, watchdog, Core task
and timer adapters. It is compiled with the pinned Xtensa compiler and the
official Arduino ESP32 1.0.1 reference identified by the original SDK string.
No application entry point or installable image is generated yet.

| Resource | Observed configuration | Evidence |
|---|---|---|
| SPI | Bus 2, mode 0, 4 MHz; SCK 17, MISO 5, MOSI 16, no hardware SS | System constructor `0x40110aa8`, setup `0x40112f88` |
| Sensor I²C | Peripheral 0; SDA 22, SCL 23, 400 kHz | `0x40112f88`; global Wire initializer `0x40125ae0` |
| Controller I²C | Peripheral 1; SDA 25, SCL 26, 400 kHz | Same constructor/setup/initializer |
| Expected sensor addresses | `0x19`, `0x34`, `0x76` | System constructor's expected-device sets |
| MSP address | `0x40` on peripheral 1 | Core constructor; polling 1000 ms and two 5 ms delays |
| Display power | GPIO 33 | `0x400d5b24`, Core setup |
| Heater output / enable | GPIO 12 / GPIO 19 | Core constructor, heater setup and enable method |
| Slow heater timer | Timer 0, divider 80, count up, edge interrupt, 1,000,000 ticks, autoreload | Core setup and callback `0x400805dc` |
| Fast heater timer | Timer 1, same options, 20,000 ticks | Core setup and callback `0x40080540` |
| Buzzer timer | FreeRTOS periodic timer, 1000 ticks, ID 1, callback `0x40080570`; start waits 10 ticks | Core setup |
| Task watchdog | 45 seconds, panic enabled, current task registered | System setup `0x40112f88` |

The software timer period is expressed in RTOS ticks, not silently renamed
milliseconds. The I²C scan in `0x40112dec` tests every address 0–127 and compares
acknowledgements with expected sets. The adapter retains that range. It
reports found/missing addresses but does not assert physical model identity.

The MSP receive adapter preserves the original unbounded availability wait
with `yield()`. Any future timeout/cancellation policy is a separate modified
firmware decision. Target compilation verifies SDK signatures and object
generation; it does not establish interrupt timing, cache safety, electrical
behavior or successful boot. Timer callback targets and complete Core object
lifetimes still belong to the eventual application assembly.

## Integrated setup and required components

`setup_core_controls` follows original `0x40113078` ordering and calls the
recovered ADC and heater implementations. It requires every remaining
component callback and stops on an explicit failure. There are no default
successful stand-ins for unrecovered components. `core_stage_evidence`
provides the address and Core offset for each setup boundary.

Both original boiler setup traces match **92 observable events** in total:
component order, display/heater pins, ADC transactions, boiler reads, timer
creation, attachment, alarm periods, and enabling. The original Core body is
executed with explicit component/SDK boundaries. ADC/heater effects at those
boundaries expand separately validated component traces; they are not counted
as nested instruction execution in this particular check. Failure-path tests
separately establish that absent components and timer failures cannot produce
a successful setup result.

The original `EventQ` objects observed in Core/Head use application-level
pending flags and payloads. They should not be silently replaced with an
invented FreeRTOS queue model. The RTOS task/timers are a separate layer.

## Reproduction

```sh
python3 tools/recover_startup.py --export <expanded-callback-export>
# Execute EmulateCoreStartup.java in the preserved project with
# -noanalysis -readOnly; its single argument is an absolute output JSON path.
python3 tools/validate_core_startup.py --original build/core-startup-original.json \
  --export <preserved-export> --write-evidence
python3 tools/build_esp32_objects.py --toolchain <pinned-xtensa-toolchain> \
  --arduino <pinned-arduino-1.0.1-checkout> \
  --arduinojson <pinned-arduinojson-checkout>
```

The target builder verifies the historical SDK's recorded identities and
produces an object archive plus a build report. It deliberately does not select
an unknown device partition layout or package these partial modules as firmware.
